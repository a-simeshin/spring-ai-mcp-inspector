src/App.tsx: onValueChange only sets the hash, not the state directly.
The upstream handler calls both setActiveTab(value) and
window.location.hash = value, while the hashchange listener also
calls setActiveTab. A controlled reproduction on the exact base
commit 770b13d5 (real Chromium 156 via Playwright, real clicks,
CPU throttling 1x-20x, 194 navigations across three click
patterns) found no divergence between the active tab trigger and
the active panel, so no race is claimed. The change is a simplification: the hashchange
listener becomes the single source of truth for tab state and the
redundant synchronous setState is removed. Covered by the three
regression tests in App.tabClickRegression.test.tsx (t_c0dcfe9a,
t_f91ff901): pane switching on click, pane switching through the
hashchange path with deterministic dispatch order, and a
click-through of every remaining tab.
